## 1. Operating rule

This plan is a query/intent architecture, not a publishing quota. A keyword family can contain many spelling and question variants while one canonical URL owns the primary user job. New URLs are created only when fresh SERP evidence, current-site/GSC ownership review when available, source-of-truth, cannibalization, canonical/slug and internal-link gates support a separate owner.

Unavailable search volume, keyword difficulty, CPC, ranking position and traffic potential remain `UNKNOWN`. Business facts about Viettel packages, prices, benefits, eligibility, registration conditions or coverage require an identified Viettel/source-of-truth record.

## 3. Expansion universe — HOLD until promotion evidence passes

### Price bands

Candidate families: 70k, 90k, 100k, 120k, 135k, 150k. Proposed clean landings remain HOLD. A price page is promoted only if search results and first-party query/page evidence show a durable price-band job that is not adequately owned by `/goi-cuoc/` or package entities.

### Data per day

Candidate families: 1 GB/day, 1.5 GB/day, 2 GB/day, 4 GB/day, 5 GB/day, 6 GB/day. Finder/filter states stay non-indexable by default. A clean landing may be approved only when it offers a meaningful package set and independent search value.

### Comparisons

Priority candidates include `5G135 vs 5G150`, `SD90 vs SD120` and the `MXH100 vs MXH120 vs MXH150` family. Comparison URLs remain HOLD until the SERP job is demonstrably distinct from the package entity pages and both sides have fresh source-of-truth facts.

### Audience/use cases

Candidate families include student, gaming, office/work and hotspot/tethering. These must not become thin recommendation clones. Suitability claims need explicit criteria from verified package attributes; eligibility, speed, latency or performance claims are not inferred without evidence.

### Duration

Candidate families include 1 day, 7 days and 12 months. The one-year intent has first-party evidence, but the exact package inventory and target architecture must be verified before an indexable landing is approved.

## 4. Query-family model

The keyword universe deliberately stores query patterns rather than producing one URL per wording. Examples:

- `5G150 | gói 5G150 | 5G150 giá bao nhiêu | 5G150 bao nhiêu GB | đăng ký 5G150` → `/goi-cuoc/5g150/`.
- `gói TikTok Viettel | gói YouTube Viettel | gói Facebook Viettel` → `/goi-cuoc/mang-xa-hoi/` unless a future SERP job proves a distinct canonical owner.
- `kiểm tra dung lượng Viettel | kiểm tra data Viettel | kiểm tra gói đang dùng` → existing package/data-check support owner.
- `hủy MXH120 | cách hủy gói MXH120 | hủy gia hạn MXH120` → existing MXH120 cancellation support owner, not the commercial package page.

This model can expand to hundreds of query variants without creating hundreds of near-duplicate pages.

## 5. AEO/GEO layer

For each retained entity/hub, map concise answer-first questions into the canonical owner rather than making standalone FAQ URLs by default. For package entities this includes: what the package is, current verified price/cycle/data, who can use it when sourced, registration path, differences versus adjacent packages, renewal/cancellation path when verified, and source/update date.

Every answer involving a Viettel business fact must preserve source provenance and freshness. Schema must reflect visible page content, not create unsupported claims.

## 6. Finder strategy

The package finder is a UI/product advantage, not an automatic index factory. Filters may include budget, data/day, voice, social apps, 4G/5G and duration. Parameter combinations remain non-indexable by default. A clean result landing is considered only after K0 promotes that exact intent from HOLD to an approved canonical owner.

## 7. Cannibalization locks

- Homepage = brand/navigation/finder entry; `/goi-cuoc/` = generic commercial package owner.
- `/goi-cuoc/5g/` remains generic 5G owner; do not duplicate with `/5g-viettel/`.
- `/goi-cuoc/data/` remains generic data owner; do not duplicate with `/goi-data-viettel/`.
- Category pages own generic category jobs; package pages own exact package-code jobs.
- `/goi-cuoc/mxh120/` owns MXH120 commercial/entity intent; `/posts/cach-huy-goi-mxh120/` owns cancellation intent.
- Comparison, price, data/day, duration and use-case proposals remain HOLD until independent ownership is proven.
- Finder query parameters are non-indexable by default.

## 8. Delivery waves

### Wave 1 — strengthen current owners

Prioritize index health and content completeness for retained P0/P1 hubs, all verified package entities and strongest support URLs. Connect category → package → support/comparison relationships with deliberate internal links. Do not alter an existing ranking URL only to make taxonomy look cleaner.

### Wave 2 — promote evidence-backed commercial gaps

Use current SERPs plus Search Console query/page data when available to choose only the strongest price, data/day and comparison candidates. Each promotion requires a K0 decision update, canonical owner, cannibalization resolution, source freshness and internal-link plan.

### Wave 3 — use-case/duration expansion

Promote audience, gaming, office, hotspot or duration pages only when there is genuine information gain, adequate verified package inventory and a distinct search job.

## 9. Search Console feedback loop

When a current Search Console export is available, feed it back into K0 to identify:

- queries with impressions but no explicit owner;
- positions roughly 4–20 worth improving;
- low-CTR pages with relevant impressions;
- unexpected query-to-page ownership;
- multiple pages receiving impressions for the same primary job;
- candidate pages that should be update/merge instead of new URLs.

No GSC values are asserted in this plan because a current first-party export was not available in this execution.
